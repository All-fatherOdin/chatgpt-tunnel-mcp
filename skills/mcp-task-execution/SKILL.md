# Выполнение MCP-задания

Совместимость: chatgpt-tunnel-mcp 0.3.x, schemaVersion 1; workflow 1.0.0. Получай актуальные схемы из инструментов.

## Получить и принять

Найди worker с get_task/claim_task/submit_report через доступный поиск инструментов. Не определяй роль по приложению или имени probe. Наличие planner-tools в Codex не разрешает исполнителю принимать собственный отчёт.

Проверь projectId по привязке и list_projects; сопоставь локальную рабочую папку с разрешённым продуктом, не угадывая абсолютный root по публичному MCP-ответу. Прочитай get_task, инструкции продукта и sourceRefs. SHA-256 относится ко всему файлу. При несовпадении выясни причину: завершённое изменение родительской задачи, текущие изменения или устаревший контекст. Не откатывай файлы под старый SHA. Неопределённость, влияющая на выполнение, блокирует зависимый шаг.

Память другого проекта читай отдельно по её projectId. Соблюдай текущие указания и действующие правила; memory не заменяет код и не расширяет scope. Поручение пользователя выполнить Task даёт основание работать в согласованном объёме; очередь сама не является поручением.

- queued: claim_task с актуальной expectedRevision и новым UUID; до успешного claim не начинай изменения.
- in_progress: продолжай только при подтверждённом владении текущим worker principal и сохранённом поручении. При параллельных исполнителях один principal не доказывает, что другой процесс не работает: проверь контекст координации.
- reported: прочитай существующий отчёт; второй итоговый отчёт не создавай.
- accepted/changes_requested/cancelled: не переоткрывай. Для доработки нужен новый Task с parentTaskId; если он уже создан, работай по новому ID.

NOT_FOUND не доказывает отсутствия Task: сравни projectId, доступы и актуальность подключения. Если planner видит задачу, а worker нет, сообщи оператору о возможном config/allowlist/store mismatch. Не меняй principal, права или SQLite самостоятельно.

## Выполнить и отчитаться

Применяй процедуры разработки продукта: разрешённые пути, ветки, тесты и правила памяти. Не фиксируй универсальные команды в этом скилле. Commit/push/deploy и реальные POST/PATCH выполняй только в границах действующего поручения и разрешённой среды/данных. Не считай отсутствие доступа успешной проверкой.

Для нового submit_report перечитай состояние/revision. Покрой каждый criterionId ровно один раз через met/unmet/not_verified. Укажи outcome completed/blocked/failed, changes, checks, criterionResults, limitations, questions по схеме. В blocked обязательны непустые limitations и questions. Сетевое evidence должно различать фактические method/status/payload и mock; исключи токены, персональные данные и секреты. Хеши и результаты тестов приводятся только если реально получены. Уже проверенное повторяй при изменении, сбое, существенном сомнении или требовании продукта.

Сохрани точные аргументы, UUID и ответ в контексте или разрешённом receipt-месте вне несогласованного scope. После timeout сначала get_task/get_report; при повторе сохрани весь исходный payload, UUID и исходную expectedRevision. Возвращённый старый reported/revision не отменяет более позднее accepted: текущее состояние проверяй get_task. Потерянный запрос не реконструируй приблизительно. CONFLICT новой операции требует перечитать состояние; IDEMPOTENCY_CONFLICT — сравнить receipt, не сменить ключ вслепую.

Итог: projectId/taskId/reportId, текущий state, реальные проверки и ограничения. reported означает передачу на приёмку, не accepted. Если отчёт не отправлен — явно укажи это и причину.
