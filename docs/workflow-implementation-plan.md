# План реализации переиспользуемого workflow

Дата: 2026-09-14. Комплект workflow 1.0.0 для сервера 0.3.x, контракт данных v1.
Область: общие инструкции, три скилла, привязка продукта, генерация инструкций и установка. API и код продуктов не меняются.

## Правила и места реализации

| Правило | Реализация | Проверка результата |
| --- | --- | --- |
| Роль определяется подключением и поручением, не приложением | Постоянные инструкции + шаг discovery каждого скилла | Planner может находиться в Codex; worker не принимает свой отчёт даже при наличии planner-tools |
| Предложение не равно передаче | Planning различает draft и publish по намерению пользователя | «Подготовь предложение» не вызывает create_task; «передай» не требует повторного согласия |
| Привязка не выдаёт права | Отдельный строгий JSON с projectId, источниками и логическими ролями подключений | Генератор не меняет MCP-конфиги и не расширяет allowlist |
| Проверить проект до claim | Execution сверяет list_projects, рабочую папку и sourceRefs | Неизвестный ID/несовпадение папки блокирует мутацию |
| Источники имеют разный авторитет | Привязка перечисляет вторичную память; инструкции требуют читать действующие правила и код | Документ памяти не доказывает поведение и не разрешает изменения |
| Ссылки принадлежат task.projectId | Planning не переносит путь из memory-проекта в sourceRefs продукта | Межпроектные источники читаются отдельно; нужные ограничения явно включаются в задание |
| Scope и критерии конкретны | Planning требует воспроизводимый результат, разрешённые пути и границы проверок | Реальный backend-контракт не подменяется созданным исполнителем mock |
| UUID и точный повтор | Все скиллы хранят исходный запрос и ключ в контексте/разрешённом receipt | Сбой после commit: сначала чтение, затем точный повтор, без новой revision |
| NOT_FOUND не доказывает удаление | Recovery описывает allowlist, конфиг, principal и store mismatch | Нет автоматического создания дубля, смены principal или правки SQLite |
| Один итоговый отчёт на задание | Execution проверяет state перед продолжением | reported/accepted/changes_requested не получают второй submit_report |
| Полный и честный отчёт | Execution покрывает каждый criterionId ровно один раз, отделяет passed/not_run | blocked содержит limitations и questions; сетевой тест описывает реальные факты без секретов |
| Независимая приёмка | Review сопоставляет критерии, код и evidence | Отчёт о тесте не становится независимо воспроизведённым тестом |
| Доработка сохраняет историю | Review создаёт follow-up с parentTaskId только при поручении | Исходное changes_requested не переводится обратно в queued |
| Нет скрытых внешних действий | Обе роли сохраняют отдельные границы commit/push/merge/deploy и сетевых мутаций | Scope задания не заменяет разрешение пользователя или ограничения среды |
| Процедура переносима | Общие скиллы не содержат GIS, абсолютных путей, веток и команд продукта | Генерация для двух разных binding без редактирования скиллов |
| Установка обратима и не стирает пользовательскую работу | CLI ставит в новый каталог; update только при совпадении хешей установленной версии | Изменённая вручную установка отклоняет update; нет массового удаления |

## Скиллы

1. `mcp-task-planning`: discovery planner → источники → draft/publish → ограниченный Task → сохранённый ответ. Follow-up получает только оставшийся объём, актуальные sourceRefs и исходный parentTaskId.
2. `mcp-task-execution`: discovery worker → чтение → проверка контекста/авторизации → claim → работа по правилам продукта → полный Report → проверка receipt. Отдельные ветви queued, in_progress, reported и терминальных состояний.
3. `mcp-report-review`: discovery planner → task/report/review → независимая проверка → решение или анализ без мутации → при поручении связанное задание. Не добавляет новые критерии задним числом.

Каждый скилл самодостаточен после установки; короткие необходимые инварианты в SKILL.md, без ссылок за пределы установленного каталога. Полная таблица lifecycle хранится один раз в reusable-workflow.md. Машинные схемы остаются в src/exchange/schemas.ts.

## Артефакты и порядок

1. Сохранить этот план до реализации.
2. Создать instructions/chatgpt-planner.md и codex-worker.md, пригодные для самостоятельного использования без активации Codex skill в ChatGPT.
3. Создать три SKILL.md с точными триггерами и краткой UI-метаинформацией; автоматический выбор включён по умолчанию.
4. Создать JSON-шаблон binding без реальных путей, ключей и данных клиентов. Создать шаблон сборки инструкций ChatGPT.
5. Реализовать CLI: validate binding, render для planner/worker, install/update одного выбранного скилла. По умолчанию target установки — CODEX_HOME/skills или ~/.codex/skills. Новые конфиги MCP, проектные AGENTS.md и ChatGPT настройки автоматически не переписывать.
6. Проверить frontmatter валидатором skill-creator, ссылки и версии, валидность примеров против реальных схем, переносимость renderer, защиту update от локальных изменений.
7. Прогнать typecheck и полный набор тестов. Поставить общий execution skill в локальный Codex, подготовить локальные инструкции GIS из существующей привязки. Исходные GIS и memory документы оставить без изменения.

## Приёмка

Проверки поведения по сценариям: draft без передачи; planner в Codex; worker NOT_FOUND при доступном planner; timeout после submit; stale SHA; reported после claim; self-review; запрос reopen; недоказанный backend payload; отсутствующая тестовая среда. Ожидаемые решения фиксируются в docs/workflow-scenarios.md. Проверка текста и схем не объявляется полноценным прогоном поведения модели; реальное применение скилла в новой сессии остаётся отдельным наблюдаемым шагом.

## Результат реализации 2026-09-14

- Созданы все три скилла с самостоятельными инструкциями и agents/openai.yaml; системный quick_validate прошёл для каждого.
- Созданы постоянные роли, JSON binding, генератор инструкций, управляемый установщик и проверяемые примеры MCP-запросов.
- Typecheck и 15 MCP-тестов прошли. Все 6 workflow-тестов прошли, включая обновление с backup, отказ от локально изменённого скилла, junction и перезаписи существующих инструкций.
- Общий mcp-task-execution установлен в пользовательский каталог Codex. Planning/review доступны в исходниках и устанавливаются отдельно, когда эти роли нужны в Codex.
- Из действующей привязки GIS подготовлены local/gis.workflow-binding.json, local/gis.chatgpt-instructions.md и local/gis.codex-instructions.md. Эти файлы исключены из Git. Продукт и внешняя память не изменены.
- Копирование нового planner-текста в ChatGPT и первое применение установленного execution-скилла в новой сессии не выполнены автоматически. Поведенческий прогон модели с новым скиллом не объявляется пройденным.
