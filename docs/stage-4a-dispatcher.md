# Этап 4A: автоматический исполнитель Codex

Версия сервера и диспетчера: 0.4.0. Дата: 2026-09-15.

Диспетчер опрашивает очередь, принимает явно разрешённое задание, запускает локальный Codex App Server и сохраняет отчёт в существующий exchange. Планировщик читает результат через `get_task` / `get_report`. Пробуждение разговора ChatGPT и автоматическое ревью относятся к 4B и здесь не реализованы.

## Границы и компоненты

- `src/dispatcher/index.ts`: отдельный CLI, непрерывный опрос, однократный проход, состояние, проверка моделей и восстановление.
- `config.ts`: строгий локальный конфиг; worker-профиль, разрешённые проекты, planner principals и scope.
- `dispatcher.ts`: claim, выбор настроек/сессии, проверка sourceRefs, запуск, получение и доставка результата.
- `codex.ts`: stdio JSON-RPC к `codex app-server`, события хода, Structured Outputs, запрет фонового предоставления согласий/ответов пользователя.
- `store.ts`: отдельная SQLite-база с WAL/FULL, блокировкой одного диспетчера и сохранёнными точными запросами claim/report.
- `workspace.ts`: чтение ветки, HEAD и признака незакоммиченных изменений; Git-мутаций нет.
- `src/exchange/execution-status.ts`: опциональная read-only-проекция состояния запуска для `get_task`.

MCP-сервер сам не запускает shell, Git или Codex. Диспетчер использует существующий `ExchangeService` с ролью worker и не изменяет SQLite-таблицы exchange напрямую. Итоговый Report по-прежнему один на Task; самостоятельной приёмки, merge/deploy нет.

## Включение

1. Собрать проект: `npm.cmd install`, затем `npm.cmd run build`.
2. Обновить и перезапустить оба MCP-процесса на версии 0.4.0. Старые поля и схема SQLite v1 сохранены, но старые строгие 0.3-клиенты не обязаны принимать новые поля Task/Report. Перед обновлением действующей базы использовать существующую процедуру backup.
3. Скопировать `config/example-dispatcher.json` в игнорируемый `config/dispatcher.local.json`.
4. Указать существующий worker-профиль, абсолютный `statePath` вне всех project roots и отдельно от exchange.sqlite, реальный путь к `codex.exe`, разрешённый projectId и principal планировщика. Для каталога состояния действует та же локальная защита DACL, что для exchange.
5. Ограничить `allowedPaths` или явно включить `allowWholeProject`. Установить `enabled: true` на уровне диспетчера и нужного проекта. В образце оба флага выключены. Рабочая папка берётся только из worker-профиля; Task не может назначить произвольную папку или команду.
6. Проверить доступность модели командой doctor и запустить диспетчер.

```powershell
# Показывает фактический каталог моделей и уровней рассуждения, без запуска модельного хода.
npm.cmd run dispatcher -- --config config/dispatcher.local.json --doctor

# Один проход по разрешённым queued-задачам и незавершённым безопасным фазам журнала.
npm.cmd run dispatcher -- --config config/dispatcher.local.json --once

# Непрерывный процесс. Для приёма новых задач он должен оставаться запущенным.
npm.cmd run dispatcher -- --config config/dispatcher.local.json

# Состояние журнала; не запускает Codex и не создаёт базу журнала.
npm.cmd run dispatcher -- --config config/dispatcher.local.json --status
```

На Windows путь к бинарнику можно найти через `Get-Command codex.exe`. `.cmd`, `.bat` и `.ps1` как codexCommand не поддерживаются: запуск выполняется с `shell: false`. Для npm-установки без отдельного exe допускаются `codexCommand` = абсолютный путь к `node.exe`, `codexArgs` = массив с абсолютным путём к CLI JS entrypoint. Пути и аргументы задаёт только оператор в локальном конфиге. Диспетчер не переписывает авторизацию Codex и не создаёт API-ключи.

Автозапуск Windows при входе в систему и установка службы не выполняются. Существующий лаунчер туннеля не переключается на диспетчер.

### Статус в ChatGPT / Codex

Для проекции состояния добавьте в `exchange` planner-профиля:

```json
{
  "dispatcherStatePath": "C:/Users/YOU/AppData/Local/chatgpt-tunnel-mcp/dispatcher.sqlite"
}
```

Это одно дополнительное поле в существующем блоке `exchange`, не полный конфиг. Оно должно указывать на `statePath` диспетчера, чей worker использует ту же exchange-базу. Поле можно добавить также в worker-профиль; тогда пути обязаны совпадать. Перезапустите соответствующий MCP-процесс.

`get_task.executionStatus` показывает фазу, время обновления, attention-код, модель, уровень рассуждения, threadId/turnId и причину выбора сессии. Абсолютные пути, prompt, аргументы claim/report не возвращаются. Без проекции результат всё равно доступен в `Report.execution` после доставки.

Проекция запуска и Task читаются из разных баз: это два текущих снимка, а не общая транзакция. Lifecycle Task/Report/Review остаётся атомарным в exchange. При временном расхождении ориентируйтесь на Task и повторите чтение. Недоступная подключённая база состояния возвращает безопасный `STORAGE_UNAVAILABLE`; `get_report` от неё не зависит.

## Разрешение на исполнение

Нужны одновременно:

1. Включённый диспетчер и включённый проект в его локальном конфиге.
2. projectId в worker allowlist и создатель задания в `allowedPlannerIds`.
3. Scope задания укладывается в локальные `allowedPaths` либо разрешён `allowWholeProject`.
4. В самом задании задано `execution.autoStart: true`.

Старые задания и `autoStart: false` остаются ручными. Обычное появление в очереди не является разрешением. Например, к существующему запросу `create_task` добавляется:

```json
{
  "execution": {
    "autoStart": true,
    "model": "gpt-5.6-sol",
    "reasoningEffort": "medium",
    "session": { "mode": "auto" }
  }
}
```

ChatGPT и Codex используют один и тот же контракт. Пользовательское поручение «передай на автоматическое выполнение» отражается в autoStart; просьба подготовить предложение его не включает. Scope и sourceRefs задаются обычными полями Task. Перед модельным ходом диспетчер проверяет хеши sourceRefs. При изменившемся/недоступном источнике возвращается blocked-отчёт, ход Codex не запускается.

Локальный допуск scope проверяет поручение, а не каждый системный вызов модели. Sandbox ограничивает рабочую среду; `allowedPaths` внутри проекта и запрет неразрешённых внешних действий дополнительно передаются исполнителю как инструкции. Это не файловая изоляция на уровне каждого подкаталога. Доступные плагины/MCP и пользовательские инструкции Codex зависят от его локальной конфигурации; для чувствительных проектов используйте соответствующий профиль доступа. Диспетчер не выдаёт новых прав и не обходит запросы подтверждения.

## Модель и переопределения

Приоритет каждого поля отдельно:

`CLI-переопределение запуска → execution в Task → projects[].executor → executor в конфиге`.

Если reasoningEffort нигде не задан, используется defaultReasoningEffort выбранной модели из `model/list`. Неизвестная модель или неподдерживаемый effort останавливают запуск до claim: `MODEL_UNAVAILABLE` / `REASONING_EFFORT_UNAVAILABLE`. Молчаливой подмены нет. Если App Server вернул другую модель/effort, выполнение не начинается.

```powershell
npm.cmd run dispatcher -- --config config/dispatcher.local.json --once --task TASK_UUID --model gpt-6-astra --effort high
```

Переопределение относится только к указанному заданию. До claim его можно исправить этой же командой, в том числе после ошибки выбора модели. После claim настройки заморожены; recovery их не меняет. Задание в exchange остаётся неизменяемым: настройки запуска и их источник сохраняются в журнале и `Report.execution`.

Запись настроек «по умолчанию для проекта» означает изменение локального `projects[].executor`. Удалённый MCP-клиент не может менять локальный конфиг. Для переопределения через чат используйте `execution` при создании Task; изменение уже опубликованного Task по-прежнему требует нового связанного задания или локального CLI-переопределения до claim.

## Сессии

Task, Run и threadId — разные сущности. В 4A один Task имеет одну запись Run; доставка и восстановление продолжают эту запись. Несколько связанных Task могут использовать один threadId. Проект обрабатывается последовательно; неопределённый исполняющийся Run блокирует запуск следующих задач этого проекта.

| Режим | Поведение |
| --- | --- |
| auto / отсутствует | Новая цель — новый thread. Follow-up после changes_requested может продолжить thread родителя |
| new | Новый thread; при наличии parentTaskId передаётся предыдущий отчёт и решение ревью |
| resume + threadId | Продолжение известного диспетчеру thread этого проекта и рабочей папки |
| fork + threadId | Ответвление известного thread с историей |

Автоматическое продолжение требует завершённого Run родителя, отсутствия более поздней работы в его thread и числа задач меньше `maxSessionTasks` (по умолчанию 5). При известном изменении Git-ветки/HEAD начинается новая сессия. Явное продолжение при таком изменении отклоняется. Непригодная сессия не выбирается по имени или признаку «последняя в проекте».

При достижении лимита, принятом предыдущем этапе, смене Git-состояния или другой работе в сессии создаётся новый thread. Передача включает цель родителя, sourceRefs, Report с изменениями/проверками/ограничениями, Review и известное состояние Git. Это исторические сведения, которые исполнитель сверяет с текущими файлами. Для проектов без Git выбор опирается на projectId, рабочую папку и цепочку заданий. Проверка dirty-флага не заменяет проверку актуальных файлов.

```powershell
npm.cmd run dispatcher -- --config config/dispatcher.local.json --once --task TASK_UUID --session new
npm.cmd run dispatcher -- --config config/dispatcher.local.json --once --task TASK_UUID --session resume --thread THREAD_ID
```

Смена модели сама по себе не требует новой сессии. Fork копирует историю и не является очисткой контекста. Принудительное сжатие по токенам в 4A не реализовано: применяется граница количества связанных задач и обычное управление контекстом Codex. Значение maxSessionTasks — настраиваемая эвристика, не универсальная норма.

## Сбои и восстановление

Фазы журнала: `prepared → claimed → starting → running → delivering → done`. `attention` — отдельный признак необходимости разбора, исходная фаза сохраняется.

- Перед claim сохраняется точный запрос с UUID/revision. После неоднозначного commit повторяется он же; чужое владение не присваивается.
- threadId сохраняется до turn/start. Фаза starting сохраняется до отправки хода, turnId — после ответа.
- После получения валидного результата весь submit_report с UUID/revision сохраняется до отправки. Ошибка доставки не запускает модель повторно.
- После commit отчёта и потери ответа следующий проход находит reportId в exchange и завершает Run.
- Восстановление running/starting читает прежний ход через thread/read. Если ответ turn/start потерян, используется уникальный маркер Run в пользовательском сообщении сохранённого хода. Новый turn/start не отправляется.
- Завершённый ход с валидным JSON превращается в Report. Подтверждённый failed/interrupted превращается в failed-отчёт с явно непроверенными критериями и предупреждением о возможных изменениях.
- Если ход не найден, ещё выполняется или отчёт невалиден, Run получает attention. Содержимое изменённых файлов не считается автоматически откатившимся.
- Два диспетчера с одним журналом не работают одновременно. После смерти процесса его PID-блокировку можно заменить; неоднозначные ходы всё равно не выполняются повторно. Журнал привязан к exchange-пути и worker principal.

```powershell
# Сначала остановить старый процесс/проверить его состояние, затем:
npm.cmd run dispatcher -- --config config/dispatcher.local.json --status
npm.cmd run dispatcher -- --config config/dispatcher.local.json --once --task TASK_UUID --recover
```

`--recover` разрешает сверку старого запуска, а не повтор исполнения с нуля. Перед новой работой после неизвестного результата нужно проверить workspace и сессию; дальнейший объём оформляется новым Task. Гарантия exactly-once для произвольных изменений файлов/внешних систем не заявляется. Обеспечены идемпотентные exchange-операции и отсутствие автоматического повторного turn/start после неоднозначности.

Коды завершения CLI: 0 — проход завершён без незавершённых выбранных Run; 1 — ошибка запуска/аргументов/блокировки; 2 — после `--once` остался attention или незавершённый Run. В непрерывном режиме выводятся изменения фаз и безопасные коды, без prompt, вывода команд и секретов. Остановка Ctrl+C прекращает диспетчер; незавершённый ход нужно сверить при восстановлении. Автоматическое завершение чужих/осиротевших процессов и удаление пользовательских данных не выполняются.

## Проверка и совместимость протокола

```powershell
npm.cmd run typecheck
npm.cmd test

# Отдельная, явная проверка с настоящей моделью; использует временный проект.
$env:CHATGPT_TUNNEL_LIVE_CODEX = (Get-Command codex.exe).Source
node --test --test-name-pattern='live Codex' dist/test/dispatcher.test.js
```

Обычный набор тестов не вызывает модель. Проверяются допуски, precedence, недоступные настройки, stale sourceRefs, потеря claim/report-ответа, сохранённый outbox, восстановление старого хода, сессии и handoff, блокировка журнала, read-only-статус и реальный stdio с протокольным fixture.

Протокол сверялся с локальным `codex-cli 0.146.0` через generate-json-schema. Реальная модельная проверка 2026-09-15 прошла на gpt-5.6-sol: файл создан и независимо прочитан тестом, отчёт записан и прочитан planner-сервисом. Подробности: [приёмка 4A](experiments/2026-09-15-stage-4a-acceptance.md).

Официальные механизмы: [Codex App Server](https://learn.chatgpt.com/docs/app-server). Новая версия Codex может потребовать изменения адаптера; неподдерживаемая операция возвращает ошибку, альтернативный исполнитель молча не запускается.
