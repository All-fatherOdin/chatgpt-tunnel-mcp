# Этап 2: безопасное чтение локальных проектов

Дата: 2026-09-09.

## Реализовано

- Опциональный локальный реестр read-only проектов с публичными метаданными, навигационными входными документами, исключениями и лимитами.
- Совместимость с конфигурацией этапа 1 и инструментами `ping`, `read_probe`.
- `list_projects`, `list_files`, `read_file`, `search_text` со строгими схемами и структурированными результатами.
- Единая denylist-политика и настроенные исключения для листинга, чтения и поиска.
- Защита от неизвестного project ID, absolute/UNC/device paths, traversal, ADS и перехода по links/reparse points.
- Встроенный буквальный поиск без shell/`rg`; ограничены время, число результатов, фрагмент и размер результата.
- SHA-256 всего файла до декодирования и выбора строк, актуальное чтение, диапазоны и продолжение усечённой выдачи.
- Локально добавлен `agent-memory-kit` с требуемым абсолютным root; путь существовал. Сам путь сохранён только в исключённой из Git конфигурации. Harness не изменялся.

## Автоматически проверено

Проверки выполняются настоящим MCP-клиентом официального TypeScript SDK на временных fixtures:

- discovery, строгие схемы, output schema и read-only-аннотации всех шести инструментов;
- старый конфиг без реестра, `ping`, `read_probe`;
- два проекта и отсутствие выхода из одного root в другой;
- публичный список без абсолютных roots;
- детерминированный листинг, depth, limit и cursor;
- ranges, empty file, SHA-256 и повторное чтение после изменения;
- усечение ответа и `nextStartLine`;
- кириллица, путь с пробелами, буквальная строка со спецсимволами, отсутствие совпадений и result limit;
- исключённые `.env` и пользовательский `excludePaths` во всех обходных операциях;
- traversal, absolute, UNC и ADS paths;
- binary, invalid UTF-8 и oversized files;
- junction создаётся и фактически проверяется, когда ОС разрешает; иначе тест печатает явный diagnostic о пропуске.

Итоговый вывод команд следует фиксировать после последнего запуска `npm.cmd run typecheck` и `npm.cmd test`.

## Фактически проверено в ChatGPT

Новые инструменты этапа 2 пока не проверены в обычном ChatGPT. В этапе 1 пользователь подтвердил только `read_probe` через существующий Secure MCP Tunnel. Нельзя считать это приёмкой project tools.

## Фактически проверено в Codex

Новые инструменты через отдельное прямое MCP-подключение Codex пока не проверены. Локальный интеграционный MCP-клиент не заменяет эту проверку.

## Не проверено и почему

- ChatGPT discovery и анализ реального harness: требуется интерактивное обновление существующего подключения пользователем и новый разговор.
- Прямые вызовы из Codex: требуется добавить/перезапустить клиентскую MCP-конфигурацию пользователя.
- Строгая snapshot-консистентность cursor при конкурентном изменении дерева не предоставляется.
- Полное устранение TOCTOU между проверкой компонентов и чтением невозможно в выбранной переносимой Node.js реализации; links запрещены и canonical path проверяется перед открытием.
- Автоматическое обнаружение любых секретов не обещается: используется документированная denylist плюс локальные `excludePaths`.
- Источник расходования лимитов ChatGPT/Work/Codex остаётся отдельной гипотезой.

## Ручная приёмка

После сборки перезапустить пользовательский `tunnel-client run`, обновить discovery подключения `chatgpt-tunnel-probe`, при необходимости обновить страницу и начать новый ChatGPT-разговор. Выполнить четыре промпта из README и сохранить фактический результат отдельно. Затем повторить `list_projects`, `list_files`, `read_file`, `search_text` через прямое подключение Codex.
