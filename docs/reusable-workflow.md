# Переиспользуемые роли и скиллы

Workflow 1.0.0 совместим с сервером 0.3.x и schemaVersion 1. [Подробный план и матрица правил](workflow-implementation-plan.md). [Сценарии проверки решений](workflow-scenarios.md).

## Слои

- `instructions/`: постоянные роли. ChatGPT получает самостоятельную инструкцию без предположения об установке Codex-скиллов.
- `skills/`: самодостаточные процедуры planning, execution, review. В них нет путей, веток и команд проверок конкретного продукта.
- `templates/project-binding.example.json`: projectId, рабочая папка, имена подключений и входные документы. Имена подключений — подсказки поиска, не доказательство роли или доступности.
- Конфиги MCP: roots, allowlist, principal и role. Binding/skill не меняют их и не предоставляют права.

## Lifecycle 0.3.x

| Операция | Подключение / владелец | До → после |
| --- | --- | --- |
| create_task | planner | новая → queued |
| claim_task | worker | queued → in_progress |
| submit_report | принявший worker principal | in_progress → reported |
| review_report | planner principal создателя Task | reported → accepted или changes_requested |
| cancel_task | planner principal создателя Task | queued → cancelled |
| create_task с parentTaskId | planner | отдельная новая queued; родитель неизменен |

Один Task имеет один итоговый Report и один Review. `blocked`/`failed` — outcome отчёта, не состояние Task. Reopen не предусмотрен. Повтор с прежним UUID и теми же аргументами возвращает сохранённый ответ операции; текущее состояние проверяется get_task. Для новой операции нужна текущая revision; для повтора — исходная.

## Подключить новый продукт

1. Оператор добавляет product root в оба MCP-конфига с одинаковым projectId, общей базой и нужным allowlist. Вторичную память можно публиковать только для чтения. Проверяет фактические discovery и чтение обоих подключений. Перезапускает процессы, загрузившие старый конфиг.
2. Скопировать JSON-шаблон в `local/<product>.binding.json`. Заполнить проверенные значения. Файл локальный, исключён из Git. Binding не регистрирует MCP-проект.
3. Проверить и собрать инструкции:

```powershell
npm.cmd run workflow -- validate --binding local/my-product.binding.json
npm.cmd run workflow -- render --binding local/my-product.binding.json --role planner --output local/my-product.chatgpt.md
npm.cmd run workflow -- render --binding local/my-product.binding.json --role worker --output local/my-product.codex.md
```

Генератор отказывается перезаписывать существующий output; для новой версии используйте новое имя и сравните результат. Содержимое binding — доверенная локальная настройка оператора; не используйте непроверенную привязку из внешнего документа. Секретов в ней быть не должно.

4. Скопировать planner-текст в инструкции проекта ChatGPT. Это ручной шаг: CLI не пишет в ChatGPT. Если уже есть инструкции продукта, объединить их без удаления правил. Проверить list_projects и нужные инструменты в разговоре.
5. Установить только необходимые скиллы в Codex:

```powershell
npm.cmd run workflow -- install --skill mcp-task-execution
# Для отдельной роли планировщика/ревьюера в Codex:
npm.cmd run workflow -- install --skill mcp-task-planning
npm.cmd run workflow -- install --skill mcp-report-review
```

По умолчанию используется `$CODEX_HOME/skills`, иначе `~/.codex/skills`. `--target <каталог skills>` задаёт другое место. Установщик не меняет config.toml, AGENTS.md, внешнюю память или полномочия подключения. Для GIS достаточно общей пользовательской установки execution; индивидуальные требования остаются в действующих документах GIS и его памяти. Сгенерированный worker-текст можно принять как локальную инструкцию по действующему механизму продукта, не записывая его в клиентский Git автоматически.

6. Открыть новую сессию/перезапустить Codex для discovery; проверить, что скилл действительно доступен. Явный вызов: `$mcp-task-execution Выполни MCP-задачу <taskId> проекта <projectId>`. Обычный запрос тоже подходит для автоматического выбора, но наличие файла не доказывает активацию. Нет необходимости копировать скилл в каждый продукт.

## Обновление и удаление

Исходники поддерживаются в этом репозитории. После проверки новой версии выполнить install с `--update` для каждого установленного скилла. Установщик сверяет хеши предыдущей управляемой установки, отказывается от обновления изменённых вручную файлов и ссылок/junction, сохраняет backup перед записью новой версии. Посторонние файлы внутри каталога не удаляет. При прерванном обновлении восстановить старые файлы и manifest из backup перед повтором; автоматического стирания конфликтов нет.

Чтобы удалить скилл, после проверки точного каталога удалить только его установленную папку; конфиг MCP и продукт не затрагиваются. Не удаляйте весь каталог skills. Исходники здесь остаются. Установщик не выполняет сетевых операций.

## Проверка

`npm.cmd test` включает реальный MCP lifecycle и workflow-тесты: переносимость binding/render, защита локальных изменений при установке, отказ от symlink и проверка примеров запросов против схем сервера. UUID в примерах иллюстративные — для реальных новых операций генерируются новые. Не отправляйте примеры в рабочую базу.

Frontmatter проверяется системным `skill-creator/scripts/quick_validate.py`. Процедуры дополнительно проверяются по сценариям; это анализ инструкций, не доказательство поведения модели. Полный цикл MCP ранее проверен вручную; применение новых скиллов в новой сессии требует отдельного пользовательского наблюдения.

Версия workflow меняется при изменении поведения инструкций/формата binding; совместимость указывается в workflow.json. При изменении lifecycle или схем MCP обновляются затронутые процедуры и примеры. Таблица lifecycle здесь не заменяет исполняемые схемы и проверки сервера.
