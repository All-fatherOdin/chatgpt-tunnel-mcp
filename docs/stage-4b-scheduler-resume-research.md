# Исследование 4B: возобновление планировщика после Report

Дата: 2026-09-15. Статус: архитектурная гипотеза готова к ручному smoke-тесту.

## Цель и граница

После того как диспетчер 4A перевёл конкретный Task в `reported`, исходный
разговор планировщика должен возобновиться, прочитать Task и Report и провести
независимое ревью. Само появление Report не означает `accepted`, не разрешает
commit/push/merge/deploy и не разрешает автоматически создавать follow-up.

4B не должна давать локальному диспетчеру учётные данные ChatGPT, управлять UI
браузера или подменять роль planner. Диспетчер остаётся только worker и
доставляет Report в exchange.

## Что подтверждено

Официальная документация ChatGPT описывает два вида scheduled tasks:

- standalone-запуск начинает новый разговор;
- задача, привязанная к разговору, возвращается в тот же разговор и использует
  его контекст; такой запуск предназначен в том числе для наблюдения за долгой
  операцией и продолжения review-loop.

Поддерживаемые внешние event triggers перечислены ограниченно: Gmail, Slack и
GitHub. Событие произвольного MCP-сервера или локальной SQLite-базы в перечне
не заявлено. Следовательно, прямое событие `submit_report -> resume ChatGPT`
нельзя считать доступным контрактом. На текущей платформе реализуемая гипотеза
— polling через thread-attached heartbeat.

Источник: [Scheduled tasks — OpenAI Docs](https://learn.chatgpt.com/docs/automations).

API Conversations/Responses, ChatKit threads и Agent sessions относятся к
разговорам приложений, построенных на OpenAI API. Документация не устанавливает
их как API для записи в существующий пользовательский разговор ChatGPT.
Поэтому они не являются заменой thread-attached scheduled task в этом проекте.

## Предлагаемый контракт 4B

Heartbeat создаётся планировщиком в исходном разговоре сразу после успешного
`create_task` с `execution.autoStart: true`. В сохранённом prompt должны быть
явно зафиксированы `projectId`, `taskId` и правила ниже:

1. Читать именно этот Task через planner-подключение; не искать «последнюю»
   задачу проекта и не создавать замену при `NOT_FOUND`.
2. Для `queued` / `in_progress` и незавершённого `executionStatus` не писать
   пользователю обычный статус и дождаться следующего heartbeat.
3. При `attention`, `cancelled`, недоступном подключении или существенном
   конфликте сообщить один раз и остановить мониторинг.
4. При `reported` прочитать связанный Report, актуальные источники и доступные
   доказательства по процедуре `mcp-report-review`.
5. По умолчанию подготовить рекомендацию, но не вызывать `review_report`, если
   исходное поручение пользователя явно не включало автоматическое решение.
6. Если автоматическое решение было заранее поручено, записать ровно один
   Review с новой idempotency key и актуальной revision. Не принимать отчёт
   при недоказанном обязательном критерии.
7. После итогового сообщения остановить или завершить heartbeat, чтобы не
   повторять ревью и уведомления.

Это сохраняет разделение полномочий: worker публикует Report, а planner в
исходном разговоре читает его своим MCP-профилем. Идентификатор scheduled task
— локальная деталь ChatGPT; связывать lifecycle следует по `(projectId,
taskId)`, а не добавлять его в схему exchange v1 на первом шаге.

## Семантика «автоматического»

Polling даёт автоматическое, но не мгновенное возобновление. Прежнее утверждение
о подтверждённом минимуме в один час отозвано: пользователь передал текстовый
ответ ChatGPT, а фактическая ошибка инструмента создания не была предъявлена.
Такой ответ не устанавливает техническое ограничение.

Повторная проверка 2026-09-15: официальная страница Scheduled tasks, раздел
Schedule a task inside a chat, прямо допускает minute-based intervals.
В локальном Codex найдена сохранённая автоматизация
`gis-full-audit-wave-controller` (GIS full audit wave controller): тип heartbeat,
интервал 2 минуты, статус PAUSED, привязка к конкретному разговору. Карточка
открыта через automation_update в режиме view; конфиг не изменён. Это доказывает
наличие минутного расписания в Codex, но не фактическую частоту прошлых запусков
и не доступность того же инструмента в целевом чате ChatGPT.

Для 4B сначала требуется попытка создать heartbeat текущего разговора с
интервалом 3 минуты через доступный в нём инструмент, сохранив результат или
точную ошибку. Универсальный часовой минимум не подтверждён. Задержка зависит
от принятого расписания, очереди и доступности среды; жёсткая верхняя граница
не установлена. Доставка Report остаётся независимой от доступности ChatGPT:
если приложение или расписание временно не работает, Report сохраняется и
будет прочитан следующим успешным запуском.

Если целевой инструмент действительно отклоняет минутное расписание, часовой
вариант не удовлетворяет требованию пользователя к задержке. При наличии в UI
команды `Run now` / «Запустить сейчас» её можно использовать для диагностики. Этот
ручной запуск проверяет продолжение разговора, MCP-доступ, prompt и остановку,
но сам по себе не доказывает автоматический запуск по расписанию. Его нужно
дополнить реальным запуском по принятому расписанию без сообщения пользователя.
Репозиторий не должен эмулировать короткий event trigger через управление
браузером, неофициальные endpoints или хранение пользовательской сессии.

## Минимальный smoke-тест

1. В новом разговоре ChatGPT создать безвредный autoStart Task с одним файлом
   и сохранить точный `projectId`/`taskId`.
2. В том же разговоре попытаться создать heartbeat с интервалом 3 минуты и prompt по
   контракту выше. Зафиксировать ID/состояние scheduled task, не добавляя его в
   exchange. При отказе сохранить точную ошибку инструмента и его тип;
   текстовое объяснение модели не считать ошибкой сервиса.
3. Пока Task `queued` или `in_progress`, подтвердить отсутствие пользовательских
   сообщений и отсутствие `review_report`.
4. Дождаться реального Report от 4A без ручного сообщения в разговор.
5. Для быстрой проверки вызвать у heartbeat `Run now`; подтвердить, что запуск
   вернулся в исходный разговор, вызвал `get_task` и `get_report` для точных ID
   и сопоставил каждый criterionId.
6. Отдельно повторить тест с реальным срабатыванием по расписанию без `Run now` и без
   ручного сообщения в разговор.
7. Для первой проверки оставить решение в режиме рекомендации. Отдельным
   прогоном, после явного разрешения, проверить ровно один `review_report`.
8. Подтвердить остановку heartbeat чтением его статуса и отсутствием запусков
   после следующих двух ожидаемых сроков. Не запускать остановленный heartbeat вручную.
9. Перезапустить туннель во время ожидания и проверить, что временная ошибка не
   создаёт дубликат Task/Review и мониторинг восстанавливается.

Проходными доказательствами являются: ID scheduled task, taskId/reportId,
времена доставки и возобновления, transcript вызовов planner-tools без секретов,
reviewId при разрешённом прогоне и отсутствие повторов после остановки.

## Открытые вопросы перед реализацией

- Может ли scheduled run в целевой поверхности надёжно завершить собственный
  heartbeat, или требуется отдельное обновление статуса из разговора.
- Сохраняется ли доступ к Secure MCP Tunnel и planner-профилю в фоновом запуске
  на выбранном плане/workspace.
- Что именно происходит с пропущенными запусками после сна машины,
  закрытого приложения или недоступного туннеля: coalescing, пропуск или очередь.
- Требуется ли для автоматического `review_report` отдельный пользовательский
  opt-in на каждый Task либо достаточно устойчивой проектной политики.

До ответа smoke-тестом статус 4B: поддерживаемая архитектура определена;
end-to-end автоматическое возобновление ещё не подтверждено.
